# スピナビ移行・設計プラン

前提：ネオレムリア・ワールドの予約・決済は外部提供（ベンダー）サイトで運用中。悩み検索→セッション内容またはヒーラー（人）が出る仕組みの**オリジナル新サイト「スピナビ」**を約2ヶ月後にローンチ予定。ローンチ後、ネオレムリア・ワールドは解約・閉鎖する。

前回まとめた戦略（[miracle-collection-booking-strategy.md](./miracle-collection-booking-strategy.md)）の内容は無効にはならず、そのまま**スピナビの要件そのもの**になる。変わるのは「旧サイトを改修して実現する」のではなく「新サイトのIA・データモデル・システム要件として最初から組み込む」という点。

---

## 0. 設計方針（最重要）

残り2ヶ月間、**旧サイト（ネオレムリア・ワールド）への機能投資はしない**。

- 旧サイトに悩み診断機能を追加する、UIを作り替える、といった改修は、2ヶ月後に消えるサイトへの投資であり回収できない。
- 今この2ヶ月でやることは、「旧サイトの改修」ではなく「**スピナビへそのまま移行できる資産の整備**」に限定する。
- 旧サイトは新規予約を受け付ける現状維持のまま運用し、並行して新サイト側でIA・データ・システムを作る。

### 今、着手すべき「移行資産」

| 資産 | 今やること | 移行後の役割 |
| --- | --- | --- |
| 悩みカテゴリー | IA（情報設計）として確定 | スピナビの検索軸そのもの |
| カウンセラープロフィール | 統一フォーマットで全員分を再収集 | 新サイトへそのまま投入するマスタデータ |
| 共通初回体験商品 | 名称・価格・時間を確定 | 新サイトの商品マスタ |
| お客様の声 | 担当者別に整理・同意取得 | 新サイトのレビューデータ |
| 予約・売上データ | 記録を開始（今からでも） | 移行時の基準値、KPI測定の起点 |

これらは今すぐ着手可能で、旧サイトを一切改修せずに進められる。

## 1. スピナビの基本設計

### 1.1 検索入口は「悩み」と「人」の両方から辿れる1つの構造にする

要件は「悩みを検索すると、セッション内容が出てくる、もしくはヒーリングできる人が出てくる」。これは見た目上は2種類の入口だが、裏側は**1つのタグ設計**で両方を実現するのが正しい作り方。

```
悩みタグ（例：パートナーシップ／才能・使命／人間関係／自信 など）
   │
   ├─ 紐づく「セッション商品」一覧を表示（内容・時間・価格・担当者）
   └─ 紐づく「カウンセラー」一覧を表示（対応できる悩み・実績・空き状況）
```

同じ悩みタグを商品にもカウンセラーにも付与しておけば、「セッションから探す」「人から探す」のどちらの入口でも同じ結果に辿り着ける。前回提案した「診断で3名おすすめ」もこの構造の上に乗せられる。

### 1.2 最低限必要なデータモデル

- **悩みタグ**：カテゴリー（親）＋具体的な悩み（子）の階層
- **セッション商品**：名称、時間、価格、提供形式（オンライン／対面）、紐づく悩みタグ、担当カウンセラー
- **カウンセラー**：プロフィール、認定資格、得意な悩みタグ、提供商品、レビュー、予約可能枠
- **レビュー**：どの商品・どのカウンセラーに対するものか、点数、コメント、掲載同意の有無
- **予約**：顧客、商品、カウンセラー、日時、金額、状態（仮予約／確定／完了／キャンセル）
- **顧客**：予約履歴、購入履歴、LINE等の連携ID

このマスタ設計を今の2ヶ月で先に固めておけば、開発と並行してデータ投入を進められる。

### 1.3 予約・決済機能として引き継ぐ必要がある要件

現在ネオレムリア・ワールドが担っている機能は、最低限そのままスピナビに引き継ぐ必要がある。

- オンライン決済（クレジットカード、必要に応じて他の手段）
- カウンセラーごとの空き枠管理・カレンダー連携
- Zoom等オンラインリンクの自動発行
- 予約前の事前相談フォーム
- キャンセル・日程変更ルールの運用

加えて、前回提案した**予約後フォロー**（24時間後の感想依頼、7日後の状態確認、再予約・3回コース提案）は、旧サイトでは実現できていなかった部分なので、**スピナビでは最初から自動配信の仕組みとして組み込む**。ここが「ただの予約サイト」から「活用される予約サイト」への一番の差になる。

### 1.4 管理側（ダイナビジョン／カウンセラー）に必要な機能

- ダイナビジョン管理者：全体の予約状況、売上、担当者別KPI（前回提示した指標）のダッシュボード
- カウンセラー本人：自分の予約管理、売上確認、レビュー確認、空き枠の更新

新規で作るなら、開発初期からこのダッシュボードを組み込んでおくと、KPI運用が最初からできる状態でローンチできる。

## 2. 移行そのものの設計（見落とすと顧客とSEOを失う部分）

新サイトの機能面だけでなく、**旧→新の切替そのもの**を設計しておく必要がある。

### 2.1 URL・SEOの引き継ぎ

- 検索エンジンやSNSに残っている旧URL（`neolemuria.world/m/◯◯/`等）は、閉鎖後にアクセスすると404になり、顧客を失う。
- ローンチ時に、旧URL→新URLの**301リダイレクト**を用意するのが理想。ベンダー提供サイトでリダイレクト設定ができない場合は、最低でも旧ドメインを一定期間（半年程度）「スピナビへ移転しました」という案内ページとして維持する。

### 2.2 外部リンクの一斉張り替え

前回整理した露出先一覧（公式サイト、スピナビ自体、スピリア、LINEリッチメニュー、YouTube概要欄、Instagram、レインボーエンジェルズの店頭QR等）は、すべて旧サイトのURLを参照している。ローンチ日に**一斉に張り替えるチェックリスト**を今のうちに作成しておく。

### 2.3 データ移行

- 顧客データ、予約履歴、レビューを旧サイトからエクスポートできる期限を先に確認する（解約後はアクセスできなくなることが多い）。
- レビュー・お客様の声は「掲載同意」が取れているものだけを移行する。

### 2.4 契約解約のタイミング

- 「立ち上がり次第解約」を即日解約と読むと、旧サイトで進行中の予約（スピナビローンチ直前に入った予約）が完了できなくなるリスクがある。
- 推奨：スピナビローンチ日に**新規予約の受付を旧サイトで停止**し、既存の確定予約は旧サイト上で完了させてから解約する「並走期間（1〜2ヶ月）」を設ける。
- ベンダー契約の解約通知期限（月末締め等）を先に確認し、並走期間を踏まえて解約通知日を逆算する。

## 3. 2ヶ月ロードマップ（移行前提版）

### Week1–2
- 悩みタグ・カテゴリーのIA確定
- カウンセラー・商品マスタの入力フォーマット確定、全メンバーへ入力依頼開始
- 旧サイトは現状維持、機能追加はしない

### Week3–4
- スピナビの開発（検索・予約・決済・管理ダッシュボード）
- お客様の声・レビューの移行データ整理（同意取得含む）
- 301リダイレクト設計、外部リンク張り替えチェックリスト作成

### Week5–6
- マスタデータの投入（カウンセラー・商品・悩みタグの紐付け）
- 予約・決済・自動フォロー配信のテスト
- カウンセラー向け説明会・管理画面の使い方共有

### Week7–8（ローンチ）
- 限定メンバーでのプレオープン（β）→実予約で検証
- 全メンバーの本番データ投入
- ローンチ当日：外部リンク一斉張り替え、旧サイトは新規予約停止
- 旧サイトは進行中の予約完了まで並走 → 完了後に解約

## 4. 前回提案との対応

前回の戦略ドキュメントで挙げた項目は、そのままスピナビの要件に読み替えられる。

| 前回の提案 | スピナビでの位置づけ |
| --- | --- |
| 悩み別診断・トップページの入口変更 | スピナビの検索構造そのもの（1.1） |
| 共通初回体験商品の標準化 | 商品マスタの初期データ（1.2） |
| 露出先とリンク方法の表 | 移行時の一斉張り替えチェックリスト（2.2） |
| 予約後の自動フォロー導線 | システムに最初から組み込む機能要件（1.3） |
| 表示順位ルール・KPI | 管理ダッシュボードの仕様（1.4） |

つまり、前回の戦略を「旧サイトの改修計画」として進める必要はなく、**そのままスピナビの要件定義書として使える**。

## 5. 現時点で確認しておきたいこと（設計を進める上での前提確認）

- スピナビの開発は内製か外部委託か、決済・予約エンジンは自社開発か既存SaaS利用か（2ヶ月という期間の中で最も進行に影響する変数）
- 旧サイトのベンダー契約の解約条件（通知期限・データエクスポート可否）
- 旧サイトに登録されている顧客データ・レビューの移行同意の取り方
- 旧URLへのリダイレクトが技術的に可能か（不可能ならドメイン維持の予算確保）

これらは意思決定が必要な項目のため、次のステップとして確認・決定しておくことを推奨する。
